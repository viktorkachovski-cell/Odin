# Shared data and command contract

This file is the integration authority for both clients and the database schema. Both clients consume the same generated types and runtime validation. The task-workflow API has been on the hosted database since 2026-09-27; the multiple-assignee API (2026-11-04) has been on it since 2026-11-05 — see the compatibility notes below. Do not infer permissions from a client-supplied household ID.

## Stored model

All IDs are UUIDs. All instants are Postgres `timestamptz`, serialized as ISO 8601 UTC. Server owns timestamps and versions. Record names below are SQL names; DTOs may preserve snake_case to avoid mapping mistakes.

| Table                      | Required fields and invariants                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `profiles`                 | `user_id` PK referencing Auth, `display_name`, nullable `avatar_ref`, `locale` en/bg, `created_at`, `updated_at`; shared users see only identity needed for their household, never email                                                                                                                                                                                                                                                                                                         |
| `households`               | `id`, `name`, `seed_locale`, `created_by`, `created_at`; no task-management role hierarchy                                                                                                                                                                                                                                                                                                                                                                                                       |
| `memberships`              | PK (`household_id`,`user_id`), `status` active/inactive, timestamps; partial unique active membership on `user_id` enforces one active household                                                                                                                                                                                                                                                                                                                                                 |
| `lists`                    | `id`, `household_id`, `kind` template/active, `title`, nullable `subtitle`, nullable shared `notes` (max 5,000), `status` open/archived, `sort_order` unique within household/kind, nullable `seed_key`, `created_by`, timestamps, positive `version`; NO deadline column                                                                                                                                                                                                                        |
| `tasks`                    | `id`, `household_id`, `list_id`, `title` (1–500), nullable shared `notes` (max 5,000), `sort_order`, `completed`, `blocked` (mutually exclusive), nullable `due_at`, timestamps, positive `version`, and `assignee_id`, which since 2026-11-04 is only the legacy single-assignee projection of `task_assignees` (below), never written by a client and never the source of truth                                                                                                                |
| `task_assignees`           | `task_id`, `household_id`, `user_id`, `created_at`; PK (`task_id`,`user_id`) so a member is assigned once; composite FKs `(household_id,task_id)` → tasks (cascade) and `(household_id,user_id)` → memberships (cascade); triggers require an active member and an open active-list parent, and refuse edits (rows are added or removed, never updated); RLS enabled with **no policy and no client grant** — assignments reach clients only inside task payloads. A task has zero or more rows. |
| `task_templates`           | `id`, `household_id`, `title`, nullable `notes`, `created_by`, `created_at`; one task only, no assignment, deadline or completion state                                                                                                                                                                                                                                                                                                                                                          |
| `private.command_receipts` | actor, household, request ID, command name, canonical payload hash, successful result reference/response, creation time; unique (actor, request ID)                                                                                                                                                                                                                                                                                                                                              |
| `private.invitations`      | id, household, creator, unique token hash, expiration, nullable redeemed_by/redeemed_at/revoked_at; never expose raw tokens or hashes via table reads                                                                                                                                                                                                                                                                                                                                            |

Templates are two separate types and never mix: a **list template** is a `lists` row with `kind = 'template'` carrying its own tasks, and a **task template** is a `task_templates` row carrying one task. Saving one never writes the other, so a task template can be loaded on its own. A member-saved list template has a null `seed_key`; `unique (household_id, seed_key)` still keeps one seeded template per key per household. See `docs/features.md`.

Composite FK `(household_id,list_id)` references a unique `(household_id,id)` on lists. An assignment's composite FK references memberships and a trigger additionally verifies active status under a share lock on the membership row, so an assignment and a revocation of the same member serialise. A template task must remain unassigned, incomplete, unblocked and undated: a template task cannot have an assignment row. Enforce in SQL, not just the client. Index child FKs. New lists and tasks append under the appropriate ordering lock; use ID as a deterministic read tie-breaker.

Stored task state is `open` (`completed=false`, `blocked=false`), `blocked`, or `done`. `@odin/domain` derives the visible four statuses: an open task is Unassigned when it has no assignees and To-do when it has one or more. Assignment and text edits preserve Blocked and Done; completion and reopening never touch assignments, and the legacy completion command clears Blocked. Copying a template resets all task runtime fields.

Select projections must not leak `profiles.locale`, invite metadata or receipts to other members. Provide a security-invoker member identity projection or narrowly scoped read RPC containing only user_id, display_name, avatar_ref and active membership. Profile ownership changes use a scoped command; household selection comes from active membership.

## Read adapter API

`@odin/data` exposes `getCurrentUser`, `getMyProfile`, `getMyHousehold`, `getMembers`, `getHome`, `getList`, `getUnassigned`, `getMyTasks`, `getAllTasks`, `getTask`, `getTaskTemplates`, and a wrapper for each command below. App-specific React Query hooks wrap these pure repositories; `useCommand`, `useTaskRowActions` and `useListActions` wire commands with their invalidation sets. Clients supply platform storage and public Supabase configuration at bootstrap.

- `getHome` calls `get_home_v2()`: open list templates, then open active lists, each ordered by shared `sort_order` and ID. Summaries include notes, subtitle, version and full-list total/completed counts. Task templates are read separately by `getTaskTemplates`.
- `getList(listId)` calls `get_list_v2(p_list_id)`: one open list and all its tasks ordered `(completed ASC, sort_order ASC, id ASC)`, with full-list counts and progress.
- `getMyTasks` and `getUnassigned` call their `_v2` RPCs: full task rows plus list title from open active lists, incomplete only. **Mine** is every incomplete task whose assignment set contains the authenticated user; **Unassigned** is every incomplete task whose set is empty. The two are disjoint, a task shared by several members appears once in each assignee's Mine, and no read ever returns a task more than once (assignments are attached to the task row, never joined into the row count, so the 1,000-row ceiling, totals and progress count tasks). Both order by due timestamp ascending, undated last, then `created_at` ascending, then task ID. Android's notifications read them; screens do not.
- `getAllTasks` calls `get_all_tasks(p_due_from, p_due_before, p_undated, p_incomplete_only)`. It returns full task rows plus list title from open active lists, in the same order, including done tasks unless the overdue filter requests incomplete only. Deadline bounds are inclusive below and exclusive above; the Undated filter cannot be combined with bounds. Invalid combinations return `VALIDATION`. Both clients read it unfiltered and filter on the client with the same bounds (`features.md`).
- `getTask(taskId)` calls `get_task_v2(p_task_id)` and returns one full task with its assignment set; the parent list must be open. Missing, archived and inaccessible tasks have the same `NOT_FOUND` result. (Before 2026-11-04 it was a direct RLS select of `tasks`; installed clients still do that and see only the legacy projection below.)
- Lists, list detail and the three cross-list task collections each return one snapshot without a cursor. Above 1,000 rows they return `TOO_LARGE` instead of a partial result. Legacy paged RPCs remain callable for installed clients, with 50-row keyset pages and unchanged signatures.
- **Task payload.** Every task returned by a read or a command — list detail, the three cross-list reads, `get_task_v2` and every command that returns a task — carries `assignee_ids` (an array of distinct user IDs in ascending order; empty means unassigned) beside the stored row. `assignee_id` is still present as the **legacy projection**: the reading member's own ID when they are assigned, otherwise the lowest assigned user ID, otherwise `null`. It exists only so installed single-assignee clients keep working; new code reads `assignee_ids` (`taskAssigneeIds` in `@odin/domain`, which falls back to `assignee_id` for a payload from before the change). A direct table read (installed `getTask`, realtime payloads) sees the stored column, which is the lowest assigned user ID or null for every reader.
- Shared progress: `total === 0 ? 0 : Math.round(completed * 100 / total)`. Server aggregate and client use identical positive-half-up rounding. Test 0/0, 1/3, 2/3, 1/8, 1/1.

## Mutation envelope

Every command takes a UUID `request_id`; every edit takes `expected_version`. Derive actor from `auth.uid()`. Scope receipts to actor, command and payload; reject a request ID reused with different input. Persist successful receipt and mutation atomically. Repeating a committed request returns its original result without repeating work. Check current authorization before returning a receipt after revocation. Failed validation/conflict commands do not consume the ID. Do not automatically retry conflicts; a revised submission gets a new ID and fresh version.

Preserve successful receipt identity for MVP; do not purge receipts on an arbitrary short timer and thereby permit late duplicate creates. If response retention later changes, preserve a uniqueness tombstone and document the retry horizon. Reauthorize before revealing any stored result.

Responses are a discriminated union: `{ok:true,data:...}` or `{ok:false,error:{code,message_key,current_version?}}`. SQL RPC transport/auth errors are mapped by `@odin/data` to the same typed client error model. Do not show SQL text to users.

Codes: `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`, `CONFLICT`, `ALREADY_ASSIGNED`, `IDEMPOTENCY_MISMATCH`, `INVITE_EXPIRED`, `INVITE_USED`, `INVITE_REVOKED`, `ALREADY_IN_HOUSEHOLD`, `RATE_LIMITED`, `TOO_LARGE`, `NETWORK`, `UNKNOWN`. `TOO_LARGE` is returned only by the snapshot reads below, when a collection exceeds what one read returns. Cross-household nonexistent/inaccessible IDs produce the same non-disclosing `NOT_FOUND` shape. Validation errors identify safe field names. `NETWORK` can mean an unknown commit outcome; retry with the same ID.

All functions below are exported by `@odin/data`, accept the existing `OdinSupabaseClient`, and return `CommandResult<T>`. They do not use database command receipts or request IDs. Never put credentials or auth tokens in command receipts. Supabase owns password hashing, identity, confirmation, recovery, session issuance and rate limits.

## Concurrency and revocation

All task mutations use conditional version checks; no last-write-wins full-row overwrite. Any changed task increments its own version once. List text changes increment list version; task mutations do not invalidate unrelated list-editor versions. Claims check eligibility in the transaction. Assignment serialises with membership revocation twice over: every assignment command locks the caller's and the targets' membership rows (`FOR UPDATE`, user-id order) before reading the task, and the `task_assignees` trigger takes a share lock on the target membership, so an inactive member cannot become an assignee after validation whichever path writes.

**Assignment semantics.** A change to the set always advances the task's version exactly once (one `UPDATE` of `tasks` per command, writing the legacy projection with it), so every other client's version-checked edit sees it, realtime delivers an ordinary `tasks` hint, and every cross-list read, list detail and the household summary are invalidated by the existing `keysAffectedByTaskChange`. Replacing the set (`update_task_v3`, `set_task_assignees`) is version-checked and cannot overwrite a change it did not see; adding or removing one member is not version-checked and cannot lose another member's change. Sets are canonicalised before hashing, so a retry under the same request ID may list the same people in any order, and a request ID reused with a different set is `IDEMPOTENCY_MISMATCH`. A deferred constraint trigger fails any transaction that leaves `tasks.assignee_id` different from the lowest `task_assignees.user_id`.

Lock order: caller/target membership rows sorted by user ID, then parent list, then tasks sorted by ID. The assignment commands take the membership rows, then the task row (never the parent list, so they cannot join a cycle with the list-then-task commands). Create, delete, complete, set-state and move commands lock the open parent list before changing a task's position or completion group, then check the expected version under the task row lock. The one task-order exception is `move_task`, which locks its own task before the adjacent one; only moves lock two tasks, and they take the parent list lock first, so no cycle can form. `move_list` takes the household list-ordering lock before either list row. Invite redemption locks the user membership serialization key before invitation row. Test genuine simultaneous transactions, not sequential calls labeled concurrency.

If a future approved operation deactivates membership, its transaction clears that member's rows in `task_assignees`, rewrites `tasks.assignee_id` for the affected tasks and advances their versions once, while denying further access. `supabase/tests/concurrency.mjs` runs exactly that fixture against assignment in both orders. Do not implement a client removal button until authority/recovery rules are approved. Tests may use an internal fixture command to simulate revocation.

## Synchronization contract

Subscribe to RLS-protected list/task/membership changes for the active household, and identity updates where authorized. Treat payloads as invalidation hints, coalesced as `architecture.md` describes. Refetch every affected read (`keysAffectedBy*` in `@odin/data`); apply the result immediately in the initiating client. Keep mutation controls pending until affected reads refetch, so a rapid second action cannot send a stale version. A stale fetch cannot overwrite a newer mutation result; cancel/reconcile query requests and compare versions. On subscription establishment/reconnect, window focus, Android foreground or expired-session recovery, refetch authoritative membership then data.

Revocation must clear client household state upon denied membership/read and stop subscriptions. If a deletion/revocation event is missed, periodic membership reconciliation while active provides bounded UI staleness; it is not an authorization boundary. Server authorization is immediate. While realtime is unhealthy, refetch on a foreground fallback timer: web every 3 seconds, Android after 5 seconds backing off to once a minute and not at all offline or in the background (R12). Verify the normal connected update budget of 5 seconds; do not promise background delivery.

## Multiple-assignee compatibility — 2026-11-04

Owner amendment: a task may have several assignees (`decisions.md`). It stays
one shared task with one deadline, note and state, counted once. The change is
**additive**: `20261104190000_multiple_task_assignees.sql` adds a table,
`tasks.assignee_id` stays, no existing RPC signature, grant, error code or
payload field is removed, and six functions are new (`create_task_v3`,
`update_task_v3`, `set_task_assignees`, `add_task_assignee`,
`remove_task_assignee`, `get_task_v2`).

**Release order (required).** (1) Apply the migration to the hosted database.
(2) Deploy the web client. (3) Ship an APK. Deploying web first fails every
assignment edit with a missing-function error. Rolling the database back after
clients use the new commands is not possible without deleting assignments;
roll forward instead.

**What an installed (single-assignee) client sees.**

| Operation                                                            | Behaviour                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Reads through RPCs (`get_list_v2`, `get_list`, the cross-list reads) | Each task carries `assignee_id` = the reading member if they are assigned, else the lowest assignee, else `null`. The member therefore sees every shared task as theirs in Mine, the badge and notifications, and one name on the row.                                                                       |
| Direct read of `tasks` (installed `getTask`, realtime)               | `assignee_id` is the lowest assigned user ID, or null. A shared task shows one assignee in the installed detail screen.                                                                                                                                                                                      |
| Edit with `update_task` / `update_task_v2`                           | Succeeds and keeps every assignee when it sends the assignee it was shown. It can never reduce several assignees to one: sending any other assignee, or null, answers `CONFLICT` (`error.task_multiple_assignees`) and changes nothing; the installed client shows its generic conflict message and reloads. |
| Same commands on a task with at most one assignee                    | Unchanged: assign, reassign and clear work as before.                                                                                                                                                                                                                                                        |
| `claim_task`                                                         | Unchanged: refuses (`ALREADY_ASSIGNED`) when anyone is assigned.                                                                                                                                                                                                                                             |
| `create_task` / `create_task_v2`                                     | One assignee at most, stored as a one-member set.                                                                                                                                                                                                                                                            |
| `set_task_completed`, `set_task_state`, move, delete                 | Unchanged; they never touch assignments.                                                                                                                                                                                                                                                                     |

Known limitation of installed builds: they cannot change who a task with
several assignees is assigned to — they can edit everything else on it — until
a new APK ships. An older client that sends the assignee it was shown while
another member is concurrently added is stopped by the ordinary version check.
`@odin/contracts` parsers tolerate a payload without `assignee_ids` (the single
`assignee_id` becomes the set), so the new web client degrades safely against a
database that predates the migration for reads, but its writes need it.

`@odin/data` changes: `createTask`/`updateTask` now call the `_v3` commands and
take `assigneeIds`; `updateTask` requires `notes`; `claimTask` was removed (the
RPC remains for installed builds); `setTaskAssignees`, `addTaskAssignee` and
`removeTaskAssignee` were added; `getTask` reads `get_task_v2`;
`useTaskRowActions(client, { userId, listId })` replaces `claim`/`unassign` with
`assignMe`, `removeMe` and `clearAssignees`. Both clients were updated together.

## Editable template compatibility — 2026-10-14

`20261014130000_editable_list_templates.sql` widens seven commands without
changing a signature, payload, grant or error code: `update_list`,
`update_list_v2`, `create_task`, `create_task_v2`, `update_task`,
`update_task_v2` and `delete_task` now accept an open list template where they
previously answered `NOT_FOUND`. A create or update that gives a template task
an assignee or due date returns `VALIDATION` with the new message key
`error.template_task_runtime`; clients translate by code, so an older client
shows its generic validation message. Claim, completion, state and Delete done
keep answering `NOT_FOUND` for a template task.

Installed clients keep working: Android APK build 4 and earlier never send
these commands for a template, so they simply cannot edit one until a new APK
ships. Both clients in this change edit templates. The migration must reach the
hosted database before the web client that uses it, or a template edit there
returns `NOT_FOUND`.

## Task housekeeping compatibility — 2026-10-14

`20261014081448_batch_delete_done_and_chronological_order.sql` is additive. It
adds `delete_completed_tasks` and changes the tie-breaker of
`get_my_tasks_v2`, `get_unassigned_v2` and `get_all_tasks` from list ID to
`created_at`; no signature or payload changes. Installed clients keep working:
they never call the new command, and Android APK build 3 re-sorts the household
